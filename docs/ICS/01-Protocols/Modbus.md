# Modbus

Modbus 是 1979 年 Modicon 公司为其可编程逻辑控制器（PLC, Programmable Logic Controller）配套设计的应用层协议，Modicon 后被施耐德电气（Schneider Electric）收购。协议规范已由 Modbus 组织（Modbus Organization）公开发布，可免费下载，这一开放性是它至今仍占据工业现场存量首位的主要原因。规范文档中被引用最多的是《MODBUS Application Protocol Specification》V1.1b3，另有串行链路与 TCP/IP 两份实现指南配套。

Modbus 采用主从模型：主站发起请求，从站响应，从站之间不互相通信；较新的规范修订中这对角色改称客户端（Client）与服务器（Server）。协议不设会话，也不做能力协商，一次请求对应一个报文。

## 传输变体

| 变体 | 承载 | 编码 | 完整性校验 | 默认端口 |
|---|---|---|---|---|
| Modbus RTU | RS-485 / RS-232 串行链路 | 二进制 | CRC-16，低字节在前 | 无 |
| Modbus ASCII | RS-485 / RS-232 串行链路 | 可打印 ASCII | LRC | 无 |
| Modbus TCP | 以太网 / TCP | 二进制 | 无，仅依赖 TCP 校验和 | 502 |
| Modbus TCP Security | 以太网 / TLS over TCP | 二进制 | TLS | 802 |

RTU 帧以 3.5 个字符时间的线路静默作为帧定界；ASCII 帧以 `:` 起始、`CR LF` 结束。Modbus TCP 去掉了串行链路的校验字段，改用 7 字节的 MBAP 报头。

## 报文结构

协议数据单元（PDU, Protocol Data Unit）只有两部分：1 字节功能码，加上该功能码定义的数据域。PDU 与传输方式无关，各变体在外面套不同的头部：

- **RTU**：从站地址（1 字节）+ PDU + CRC-16（2 字节）
- **ASCII**：`:` + 地址（2 个十六进制字符）+ PDU（每字节展开为 2 个字符）+ LRC + `CR LF`
- **TCP**：MBAP 报头 + PDU

MBAP（Modbus Application Protocol header）共 7 字节：

| 字段 | 长度 | 说明 |
|---|---|---|
| 事务标识符 Transaction Identifier | 2 字节 | 主站生成，从站原样返回，用于匹配请求与响应 |
| 协议标识符 Protocol Identifier | 2 字节 | Modbus 固定为 `0x0000` |
| 长度 Length | 2 字节 | 其后所有字节的数量，即单元标识符加 PDU |
| 单元标识符 Unit Identifier | 1 字节 | 串行从站编号，取值 1–247，248–255 保留；串行链路上地址 `0` 为广播 |

## 数据模型与功能码

Modbus 把从站数据抽象为四类基本对象，地址空间为 16 位：

| 对象 | 位宽 | 读写 | 功能码 |
|---|---|---|---|
| 线圈 Coils | 1 位 | 读写 | 0x01 读、0x05 写单个、0x0F 写多个 |
| 离散输入 Discrete Inputs | 1 位 | 只读 | 0x02 读 |
| 保持寄存器 Holding Registers | 16 位 | 读写 | 0x03 读、0x06 写单个、0x10 写多个 |
| 输入寄存器 Input Registers | 16 位 | 只读 | 0x04 读 |

上述功能码在 TCP 与串行链路上均可用。0x07 读异常状态、0x08 诊断、0x0B 读通信事件计数器、0x0C 读通信事件日志、0x11 报告从站标识属于仅串行链路可用的功能码。跨两种传输的还有 0x14 读文件记录、0x15 写文件记录、0x16 屏蔽写寄存器、0x17 读写多个寄存器、0x18 读 FIFO 队列，以及 0x2B 封装接口传输——其中 MEI 类型 0x0E 为读设备标识，是设备指纹识别的常用入口。

异常响应的功能码为原功能码加 `0x80`，数据域第一个字节是异常码：0x01 非法功能、0x02 非法数据地址、0x03 非法数据值、0x04 从站设备故障、0x06 从站设备忙。

寻址存在「差一」问题：协议地址从 0 开始，而工程文档与设备面板习惯使用从 1 开始的 PLC 地址，例如保持寄存器 40001 对应协议地址 0。两套编号混用是现场误写寄存器的高频原因。

## 安全暴露面

设计层面的缺陷，协议自身无解：

- **无认证**：协议不定义任何身份验证。能到达 502 端口的主机、能挂上 RS-485 总线的设备，就是合法主站。
- **无加密**：寄存器值与线圈状态明文传输，工程站与 PLC 之间的全部控制数据可被旁路读取。
- **无完整性保护**：Modbus TCP 只依赖 TCP 校验和，无法抵御主动篡改。事务标识符由主站自选，多数实现不严格校验其连续性，伪造响应与注入响应的成本很低。
- **地址空间小且可枚举**：单元标识符有效范围 1–247，一轮扫描即可穷举在线从站及其支持的功能码集合。
- **广播写**：串行链路上向地址 0 发送写请求，所有从站同时执行且不返回响应，单次操作即可影响整条总线。
- **写操作的后果是物理性的**：改写保持寄存器或线圈直接改变执行机构动作，例如阀门开度、泵启停、联锁条件。损害无法通过恢复数据回滚，这一点与企业 IT 环境根本不同。

实现层面的缺陷，可随固件收敛，但存量设备更新缓慢：

- 畸形 PDU、超长数据域、非法长度字段导致解析崩溃或设备重启的问题在多家实现中出现过，具体 CVE 编号与受影响固件版本 待验证。
- 许多 PLC 的 Modbus 服务与厂商专有编程协议共用同一网口甚至同一端口，封禁 Modbus 不等于封禁程序下载通道，实际监听情况 待验证。
- Modbus TCP Security 的存量支持面很窄，老设备能否通过固件升级获得 TLS 支持 待验证。

## 检测方法

被动检测优先。Modbus 是周期性轮询协议，流量高度规律，这既是它的弱点也是它的检测优势。

- **抓包解析**：在镜像口或分光点采集。Wireshark 内置解析器，显示过滤器 `mbtcp` 对应 Modbus TCP，`modbus` 对应串行变体。
- **入侵检测**：Suricata 提供 Modbus 应用层解析与 `modbus` 规则关键字，可基于功能码、单元标识符与寄存器地址范围建白名单规则。Zeek 对 Modbus 的解析是否包含在核心发行版中 待验证。
- **主动枚举**：`nmap --script modbus-discover -p 502 <目标>` 可枚举从站标识与功能码支持情况。该脚本会发送真实协议请求，在未授权网络或运行中的生产网络上禁止使用；针对其他工控协议的枚举脚本名与可用性随 nmap 版本变化，待验证。
- **资产测绘**：互联网侧可用 `port:502` 这类通用过滤条件在 Shodan、Censys 等平台检索暴露资产，各平台的工控协议专用过滤字段 待验证。
- **基线偏离告警**：对轮询周期、在线从站集合、出现过的功能码集合、寄存器取值区间建立基线。新增从站或首次出现的写功能码都应触发告警。这一方法对 Modbus 尤其有效，因为正常流量几乎没有变化。
- **报文构造验证**：pymodbus、mbpoll 以及 modpoll（主站）、diagslave（从站）可在实验环境复现异常报文；Scapy 提供 `scapy.contrib.modbus` 层，便于构造畸形 PDU。

Modbus 协议自身不产生审计日志，操作溯源只能依赖旁路探针或设备侧的厂商专有日志，后者的可用性与留存粒度 待验证。

## 加固建议

- **按区域与导管分区**：参照 [IEC 62443](../03-Standards/IEC-62443.md) 的 Zone / Conduit 模型划分控制层与业务层，跨区流量走显式白名单，不做默认允许。
- **白名单粒度到寄存器**：工控防火墙或单向网关按「单元标识符 + 功能码 + 地址范围」建基线，只放行实际使用的组合；只读从站禁掉全部写功能码。
- **不暴露到互联网**：关闭不必要的 TCP 502 入站，远程维护走 VPN 或专用运维通道，不在边界防火墙上直接做端口映射。
- **串行总线做物理防护**：RS-485 总线一旦接入即等于获得完全控制权，需要机柜上锁、端子加护罩，并对总线上新增的主站做电气层面的告警。
- **新建设计选用 Modbus TCP Security**：对存量设备先做兼容性与停机窗口评估，评估结论 待验证。
- **写操作纳入变更流程**：程序下载与批量写线圈、写寄存器走变更审批。PLC 侧的保护模式或钥匙开关位置由厂商定义，具体行为 待验证。
- **备份工程文件与 PLC 程序**：写入会不可逆地改变控制逻辑，恢复依赖离线备份而不是设备自身。
- **不混用网段**：工程站、HMI 与办公终端不放在同一广播域，避免办公网侧的横向移动直接落到控制网。
